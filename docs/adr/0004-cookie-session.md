# 0004. Cookie-сессия вместо next-auth

Дата: 2026-10-15
Статус: accepted

## Контекст

next-auth привязан к Next.js. В `@tanstack/react-start` 1.169 нет `useSession`, готовой сессии из коробки тоже нет. Бэкенд выдаёт access и refresh токены, которые нельзя отдавать в JS браузера.

## Решение

Сессия хранится в httpOnly cookie `rbt_session` (sameSite lax, secure в проде, 30 дней), содержимое шифруется AES-256-GCM, ключ выводится из `SESSION_SECRET` через HKDF (`src/entities/session/api/cookie-seal.server.ts`). Тег аутентификации строго 16 байт. Серверные функции (`auth.functions.ts`) читают и пишут сессию, access-токен обновляется заранее со скосом 60 с (`REFRESH_SKEW_MS`). Защита маршрутов: `_authed` и `_guest` в `beforeLoad`. Возврат после входа: `redirect` с параметром `?redirect=` вместо `callbackUrl`.

## Последствия

- Токены не попадают в клиент, подделка cookie не проходит проверку тега.
- Файлы `*.server.ts` нельзя реэкспортировать из `index.ts` и импортировать в клиентский код.
- Смена `SESSION_SECRET` разлогинивает всех пользователей.
- Шифрование и refresh поддерживаем сами, покрыто тестами.

## Дополнения (2026-10-15)

### Grace-ответ refresh

Ротация refresh-токена на бэкенде одноразовая. При гонке (два refresh одним токеном) второй запрос в пределах `AUTH_REFRESH_RACE_GRACE_SECONDS` получает ответ без `refreshToken`: новый токен уже выдан первому. Если сохранить в cookie прежний refresh, он окажется уже ротированным, и следующий refresh бэкенд сочтёт reuse и отзовёт всю семью токенов. Поэтому ответ без `refreshToken` (`rotated: false` в `sessionFromRefresh`) не пишем в cookie: новый access живёт только в рамках текущего запроса, а cookie остаётся за тем запросом, который получил ротированный refresh. Параллельные refresh в одном процессе дополнительно схлопываются в один вызов (`inflightRefresh`). Для login, signup и password-change отсутствие `refreshToken` — ошибка контракта.

### Известное ограничение: отзыв сессии на другом устройстве

`getValidSession` проверяет только `accessTokenExpiresAt`, а не обращается к бэкенду. После logout-all или сброса пароля на другом устройстве текущая cookie-сессия считается валидной, пока не истечёт access-токен (по умолчанию `AUTH_ACCESS_TOKEN_TTL` = 15 мин). Первый защищённый вызов (`password-change`, `logout-all`) получает 401 (`{"detail": "token_revoked"}` в формате Bolt, без `code`): клиент API превращает его в `unauthorized`/`token_revoked`, серверная функция очищает cookie и просит войти заново. Дальше refresh тоже будет отклонён. Принято сознательно: проверка отзыва на каждый запрос стоила бы лишнего обращения к API.

### Выход

- `logout` при сетевой ошибке или 5xx всё равно очищает cookie и возвращает успех: локальный выход важнее. Refresh-токен на бэкенде доживёт до своего срока.
- `logoutAll` успех сообщает только после подтверждения бэкенда. При сети/5xx возвращается ошибка, cookie сохраняется, чтобы можно было повторить. При 401 cookie очищается.

### Определение IP клиента

IP и User-Agent браузера пробрасываются в бэкенд (`X-Real-IP`, `User-Agent`) при login, signup/complete, refresh и password-change, иначе в списке устройств окажется сервер приложения. `X-Forwarded-For` и `X-Real-IP` клиента подделываются, поэтому доверяем им только при `TRUST_PROXY=true` (по умолчанию `false`, IP берётся из сокета). Включать только когда приложение стоит за прокси, перезаписывающим эти заголовки; без флага за прокси в сессии будет адрес прокси.
