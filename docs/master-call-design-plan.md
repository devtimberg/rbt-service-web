# Вызвать мастера: обновление по макетам

Статус: функциональная основа реализована; визуальная часть требует отдельной доработки по замечаниям заказчика. Содержимое политики предоставит заказчик. Реальная отправка по-прежнему заменена согласованной заглушкой.

Источник: [секция «Вызов мастера — MVP» в Figma](https://www.figma.com/design/McTZS5CWwqW9iYsjhonNMz/?node-id=455-3387).
Предыдущий этап: [mvp-master-call.md](mvp-master-call.md). Его описание старых макетов не является эталоном для этого обновления.

## Результат реализации

- Обновлены форма и результат, добавлены оригинальные локальные ресурсы принтера и выезд чека за 700 мс. Длинный комментарий переносится полностью; при успехе прокрутка возвращается к заголовку результата.
- Расширен `Select`: `presentation="responsive"` открывает десктопный список или мобильную шторку через нативный dialog в верхнем слое. Старый нативный вариант сохранён для остальных вызовов.
- «Другое» раскрывает необязательное поле своего варианта. Технический лимит — 100 символов; пробелы по краям убираются при отображении/отправке. Пустой вариант отправляется как «Другое».
- Черновик хранится в `sessionStorage` под ключом `rbt:master-call:draft:v1`. Частичный телефон и скрытый свой вариант восстанавливаются. Сохраняется и временно невалидный длинный комментарий, чтобы перезагрузка не теряла введённый текст.
- Уход подтверждается общим UI-контекстом, см. [ADR 0014](adr/0014-form-navigation-confirmation.md). Диалог использует расширенный `ConfirmDialog` с вертикальными действиями для длинных подписей.
- Политика открывается в отдельной вкладке, сохраняя заполненную форму. Источник: `src/pages/privacy-policy/content/privacy-policy.md`. Сейчас в нём только служебный комментарий, страница явно показывает, что текст готовится, и закрыта от индексации. После добавления действующего текста пересмотреть `robots` в metadata.
- `Markdown` использует `react-markdown`, UI-кит и CSS Modules. Примеры рендерера и адаптивного выбора техники добавлены в `/_dev/ui`. Таблицы не включены: необходимость определится по реальному документу.
- Ошибку заглушки в dev можно включить из консоли браузера: `sessionStorage.setItem('rbt:master-call:mock-error', '1')`; отключить через `removeItem` того же ключа. В production этот переключатель не действует.
- Проверены в Chromium: десктоп и мобильная ширина, восстановление, отмена ухода, подтверждение браузерного «Назад», ошибка и повторная попытка. Production-сборка проверена в отдельной временной копии; `.md` включён в standalone и читается сервером. Общая шапка сохранена из проекта, её отличия от Figma вне текущего изменения.
- Unit- и компонентные тесты обновлены/добавлены. Перед коммитами выполнен `make ci`: проверки прошли, 41 тестовый файл и 159 тестов зелёные. Работа настоящей экранной клавиатуры требует проверки на физических iOS/Android; её обработчик дополнительно проверен имитацией изменения visualViewport.

## Исходное состояние

В коде уже есть форма на react-hook-form и zod, RTK Query с заглушкой отправки, живой чек и экран «Заявка создана». Повторно создавать их не нужно. Существующие примитивы: `Select`, `TextField`, `PhoneField`, `TextArea`, `Receipt`, `Sheet`, `Button`.

Новые макеты добавляют принтер, отдельное поле для своего варианта техники и мобильную шторку выбора. На десктопе кнопка расположена под полями; согласие находится вне чека. Сейчас кнопка использует `SheetFooterSlot` на всех ширинах, согласие находится внутри чека, а `Select` открывает системный список.

## Согласовано

- Чек заполняется по мере ввода данных.
- После успешного ответа чек выезжает из принтера; ошибка отправки не запускает анимацию, введённые данные сохраняются.
- При `prefers-reduced-motion` сразу показываем итоговое положение без движения.
- При выборе «Другое» появляется необязательное поле «Ваш вариант техники». Если оно пустое, в чеке показываем «Другое»; иначе — введённое название.
- При переключении категории свой вариант сохраняется до закрытия формы, но участвует в отправке только при выбранном «Другое».
- Комментарий до 255 символов показываем в чеке полностью, с переносами и без уменьшения шрифта. На десктопе чек растёт вверх от щели принтера, на мобильном увеличивает высоту прокручиваемой страницы.
- При росте чека его начало должно оставаться доступным: на десктопе композиция получает необходимое место по высоте и прокрутку, без обрезания верхней части. Длинные слова тоже переносятся.
- Текущий этап — дизайн и поведение с существующей заглушкой RTK Query. Подключение реальной отправки — отдельный этап после согласования контракта API. Успех заглушки не означает создание реальной заявки.
- При уходе предупреждаем, если в форме остались введённые данные; после очистки всех полей и успешной отправки предупреждение не показываем. «Продолжить заполнение» оставляет форму открытой, «Закрыть без сохранения» удаляет черновик и выполняет запрошенный переход.
- Черновик храним в `sessionStorage` текущей вкладки, без постоянного хранения в `localStorage`. При перезагрузке восстанавливаем поля, включая свой вариант техники, сохранённый при переключении категории. После успешной отправки и подтверждённого закрытия без сохранения черновик удаляем. Браузер может восстанавливать сессию вкладки; не обещаем гарантированное удаление данных при завершении процесса браузера.
- Предупреждение показываем только при уходе внутри сайта с заполненной формой. При перезагрузке и закрытии вкладки предупреждения нет, обработчик `beforeunload` для него не добавляем. Перезагрузка восстанавливает черновик из `sessionStorage`.
- Выбор техники: на мобильном открываем шторку по макету, на десктопе — выпадающий список под полем. Нажатие на вариант сразу выбирает его и закрывает список. Добавляем пункт «Не выбрано» для очистки необязательного поля; свой вариант при этом сохраняется по общему правилу переключения категории.
- На мобильном при открытой экранной клавиатуре скрываем нижнюю панель с кнопкой «Создать заявку», после закрытия возвращаем. Активное поле остаётся видимым и доступным для прокрутки.
- После успешного ответа сразу показываем «Заявка создана», номер и доступную кнопку «Хорошо». Выезд чека идёт параллельно, ориентировочно 700 мс. Кнопка доступна во время движения; уход прекращает анимацию. При `prefers-reduced-motion` результат и итоговое положение чека показываем сразу.
- Во время отправки блокируем поля и повторную отправку. Уйти можно через предупреждение о потере данных. При ошибке разблокируем форму с прежними значениями; после подтверждённого ухода поздний ответ не открывает результат и не запускает анимацию.
- Политика конфиденциальности — отдельная страница. Пользователь предоставит текст позже в `.md`; реализуем чтение Markdown и оформление через UI-кит. Готового текста политики сейчас нет.

## Этапы реализации

### 1. Зафиксировать состояния и поведение

- Разобрать форму, выбор техники, вариант «Другое», длинный комментарий и результат на обеих ширинах.
- Реализовать согласованные правила своего варианта техники, отправки, повторной попытки, черновика и ухода со страницы.
- Проверить мобильный скролл и согласованное скрытие нижней панели при экранной клавиатуре. Сам по себе фокус поля не означает открытую клавиатуру: учесть аппаратную клавиатуру и закрытие экранной без потери фокуса.
- Сверить тексты: в некоторых хлебных крошках осталось «Заказать запчасть», хотя экран относится к вызову мастера. Имена слоёв тоже содержат старые названия; эталон текста сверять по содержимому, а не имени слоя.
- Для проверки загрузки, ошибки и повторной попытки предусмотреть управляемые сценарии заглушки в среде разработки без пользовательского переключателя в интерфейсе.

### 2. Подготовить компоненты и ресурсы

- Переиспользовать примитивы и токены проекта, сравнить их параметры с новым макетом, расширять существующие компоненты при необходимости.
- Получить из Figma оригинальные ресурсы принтера, наклейки и индикатора. Сохранить ресурсы локально, без временных URL Figma в коде; использовать композицию макета без замены ресурсов похожими.
- Композицию принтера и живого чека разместить в слайсе `pages/master-call`; универсальную бумагу и строки оставить в `shared/ui/receipt`.
- Расширить существующий `Select` для списка на десктопе и шторки на мобильном, переиспользовать `Popover` и `Sheet`, предварительно проверив их возможности. Обеспечить клавиатурный выбор, обозначение выбранного пункта, закрытие без изменения значения и возврат фокуса на поле. Обновить витрину UI-кита.

### 3. Обновить форму и модель

- Добавить состояние «Другое» и поле «Ваш вариант техники» по согласованным правилам. Связать его с чеком и аргументом мутации.
- Сохранить обязательность телефона и текущий лимит комментария 255 символов, если при согласовании не решено иначе.
- Перенести согласие из чека к форме. Добавить маршрут политики в `ROUTES` и связать текст согласия с новой страницей после подготовки её содержимого и рендера Markdown. Не выдавать временный текст за действующую политику.
- Десктоп: две области, форма шириной 480 px в эталоне 1440 px, кнопка под полями. Мобильный: последовательный контент и закреплённая нижняя кнопка согласно макету; панель скрывается при экранной клавиатуре. Проверить доступную высоту и безопасные отступы в Safari и Chrome, не определять клавиатуру только по фокусу поля.
- На время запроса блокировать поля и повторную отправку, показывать загрузку кнопки. При ошибке показывать общую ошибку и разрешать повторную попытку с сохранёнными значениями. Снимок отправленных данных использовать для результата; поздний ответ после ухода игнорировать в UI. Уход не означает гарантированную отмену обработки на будущем сервере.
- Предупреждение о потере данных собрать на существующем `Dialog` с действиями «Продолжить заполнение» и «Закрыть без сохранения». Показывать до ухода внутри сайта, а не после размонтирования формы. Проверить ссылки в шапке, логотип, закрытие раздела и переходы назад/вперёд между страницами сайта. Перезагрузка и закрытие вкладки не блокируются.
- Восстановление черновика из `sessionStorage` выполнять после гидратации, сохраняя согласованный SSR. Новый глобальный стор не вводить. Проверить доступность хранилища и повреждённые данные, ошибки валидации и состояние загрузки не сохранять. Не перезаписывать сохранённый черновик пустыми значениями до завершения восстановления.

### 4. Обновить чек и сцену принтера

- Сверить типографику JetBrains Mono, отступы, края, строки, заглушку номера и тень у щели принтера с новыми компонентами Figma.
- Уточнить состав реквизитов, подписи строк и отображение пустых данных: новый макет отличается от текущего чека.
- Сделать адаптивную композицию без фиксирования высоты всей страницы по высоте макетного кадра. Длинные данные должны переноситься без наложения на форму и кнопки.
- Анимацию строить вокруг существующего чека: исходное положение в принтере → успешный ответ → выезд → итоговое положение. Номер и время брать из ответа мутации.
- Сохранить непрерывность сцены принтера и чека при смене формы на результат: смена компонента страницы не должна обрывать выезд или запускать его повторно. Не задерживать доступ к результату до завершения анимации.

### 5. Экран результата

- Переиспользовать `MasterCallCreated`, обновить композицию, размеры и отступы по новому макету.
- На десктопе разместить «Хорошо» в левой области; на мобильном сверить нижнюю панель.
- Сохранить текущее поведение: «Хорошо» ведёт на `ROUTES.HOME`. Экран успеха не сохранять в черновике: после перезагрузки успешного экрана показывается новая пустая форма, повторная отправка автоматически не выполняется.

### 6. Страница политики из Markdown

- В проекте пока нет Markdown-парсера. Рабочее предложение — `react-markdown` с сопоставлением элементов через `components`: [официальная документация](https://github.com/remarkjs/react-markdown#readme). Не писать собственный парсер регулярными выражениями. MDX и исполнение JSX для текстового документа не нужны.
- Источник текста — локальный UTF-8 файл, например `src/pages/privacy-policy/content/privacy-policy.md`. Чтение файла оставить на сервере в слайсе страницы; UI-компонент получает строку Markdown и не работает с файловой системой. Изменение документа в репозитории требует новой сборки/выкладки.
- Предлагаемый маршрут — `/privacy-policy`, константа `ROUTES.PRIVACY_POLICY`. Корневой `app/privacy-policy/page.tsx` содержит metadata и входной компонент из `src/pages/privacy-policy`; страницу по умолчанию показывать в обычном контенте, без добавления в `isSheetPath`.
- Универсальный рендерер `Markdown` разместить в `shared/ui/markdown`, экспортировать через общий барель, добавить пример в витрину. Настроить заголовки через `Heading`, абзацы/выделение через `Text`, списки через `List`/`ListItem`, ссылки через `SmartLink`, разделители через `Divider`. Недостающие примитивы добавлять только под элементы реального документа.
- Начальный набор разметки: заголовки, абзацы, маркированные и нумерованные списки, жирный/курсив, ссылки, разделители. Если предоставленный текст содержит таблицы, подключить `remark-gfm` и примитив таблицы отдельной необходимой доработкой. Сырой HTML не исполнять.
- CSS Modules: универсальные стили рендерера в `@layer components`, оформление страницы в `@layer slices`. Применить существующие токены типографики, цветов и отступов, ограничить ширину текста для чтения, обеспечить перенос длинных ссылок и адаптивные отступы. Не требовать HTML-классов внутри `.md`.
- Согласовать единый источник заголовка страницы, чтобы не получить два `h1` из шаблона и Markdown. После получения текста проверить вложенные списки, ссылки и фактические элементы разметки.
- До получения текста подготовить рендерер и витринный пример; содержимое политики остаётся незавершённой частью. Не публиковать демонстрационный текст как документ компании.
- Проверить включение `.md` в standalone-артефакт и чтение в запущенной standalone-сборке; при необходимости добавить точный путь в `outputFileTracingIncludes`. Проверить прямой заход, ссылку из формы, перезагрузку и читаемость на мобильном.

### 7. Проверка

- `make check` после изменений. Тесты запускать только по явной просьбе или перед запрошенным коммитом, согласно AGENTS.md.
- Визуально сравнить форму, «Другое», длинный комментарий, выбор техники и результат на 1440 и 402 px; проверить промежуточные и узкие ширины.
- Проверить клавиатуру, фокус и закрытие шторки, мобильную клавиатуру, скролл, загрузку, ошибку отправки, повторную попытку и `prefers-reduced-motion`.
- Проверить восстановление после перезагрузки, очистку черновика после успеха/подтверждённого ухода, отмену ухода без потери данных и поздний ответ после ухода. Проверить, что закрытие списка техники не считается уходом со страницы.
- При изменении схемы и поведения обновить соответствующие unit- и компонентные тесты; запуск — по правилам выше.

## Оставшиеся уточнения и технические проверки

1. Собрать предоставленный текст политики и проверить его фактическую Markdown-разметку; лимит своего варианта 100 и обработка пробелов реализованы.
2. Полный список техники — сверить существующие категории с макетом; сброс через «Не выбрано» согласован.
3. Высота и прокрутка мобильной шторки выбора — адаптировать к доступному месту, проверить в браузере.
4. Раскладка растущего чека и принтера на промежуточных ширинах и при небольшой высоте окна — проверить в браузере.
5. Проверить траекторию выезда на длинном чеке и обеих ширинах; последовательность и ориентировочная длительность согласованы.
6. Состав реквизитов и текстов чека; получить Markdown-текст политики. Подход к рендеру и маршрут выше — техническое предложение, финальную разметку сверить с предоставленным документом.
7. Технический охват навигации внутри сайта, включая историю браузера, без опоры на неподдерживаемый перехват маршрутизатора; детали отображения ошибок заглушки. Реальный API вынесен в отдельный этап.

Обычные изменения формы и оформления не требуют нового ADR. Если изменится принятое поведение маршрута-шторки, отдельно оценить необходимость обновления ADR 0013.
